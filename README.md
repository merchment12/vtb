# Разблокировка самозанятых по 115-ФЗ — MVP

Операции по карте банк берёт из своей учётной системы, клиент их не загружает и подделать не может.
Клиент приносит только то, чего у банка нет: чеки из «Мой налог», справки и пояснения, **одним полным
пакетом**. Система не даёт отправить неполный пакет, сопоставляет каждое поступление с чеком и собирает
для сотрудника готовую сверку с индикаторами риска. Сотрудник принимает решение или отправляет точечный запрос по конкретным
операциям, а не общую формулировку.

Почему это важно: сам ВТБ объясняет долгую разблокировку неполными документами и пояснениями
клиентов, из-за которых приходится отправлять повторный запрос (ТАСС, июль 2025).

## Запуск

```bash
uv sync
uv run python scripts/generate_samples.py   # демо-пакеты: честный репетитор и дроппер
uv run uvicorn app.main:app --reload         # http://127.0.0.1:8000 — выбор роли, API: /docs
uv run pytest
```

> Если таблицы в коде изменились, демо-база SQLite пересоздаётся при запуске сама — удалять `unblock.db` не нужно.

## Демо на защите: два экрана

Откройте http://127.0.0.1:8000 и откройте оба экрана рядом. Действия клиента появляются у сотрудника,
ответы сотрудника приходят клиенту, без перезагрузки.

**Живой сценарий (клиент → сотрудник → клиент):**

1. `/client` → «Честный репетитор» → «Начать». Операции по карте банк уже подтянул сам.
2. Загрузить чеки `samples/honest_receipts.json` и две справки (любой PDF), пояснить 4 поступления без чека, «Отправить на проверку».
3. `/staff`: кейс появился в очереди. Открыть — сверка, индикаторы, рекомендация системы, документы и переписка.
4. «Запросить документы» или «Разблокировать». Клиент сразу видит ответ в переписке; на запрос отвечает и отправляет пакет повторно.

Клиенту индикаторы риска и обоснование решения не показываются — только переписка и итог.

**Готовые кейсы для сравнения (экран сотрудника):**


1. Откройте `http://127.0.0.1:8000/staff` и нажмите **«Загрузить демо-кейсы»** — в очереди появятся три готовых пакета.
2. **Анна Смирнова** — честный репетитор: 97% дохода подтверждено чеками, одно поступление пояснено как перевод от мамы. Вердикт «низкий риск», сверка за доли секунды → «Разблокировать».
3. **Игорь Петров** — дроппер: 11% покрытия, 99% денег уходит в течение суток, превышен лимит НПД → «Запросить документы» (черновик запроса уже собран) или «Отказать».
4. **Олег Кузнецов** — скрытый доход: клиент отнёс две трети поступлений к «личным», чтобы не показывать чеки. Покрытие по оставшимся выглядит прилично, но индикатор «Поступления, отнесённые клиентом к личным» и таблица справа показывают, что система изначально считала эти деньги доходом.

Все данные синтетические. Решение и индикаторы, на которых оно принято, пишутся в журнал кейса.

## Сценарий через API (/docs)

Операции по карте для демо-клиентов уже лежат в эмуляторе банка `samples/bank_core/<ИНН>.csv`.
Свои данные можно положить туда через `PUT /api/bank-core/{inn}/statement`.

1. `POST /api/cases` — ИНН из `samples/README.json`, `block_reason: income_source`, `blocked_at: 2025-10-01`.
   Операции по карте подтянутся из банка сами.
2. `POST /api/cases/{id}/documents?doc_type=receipts` — `samples/honest_receipts.json`.
3. `...?doc_type=npd_certificate` и `income_certificate` — любой PDF.
4. `GET /api/cases/{id}/checklist` — что не хватает: 4 поступления без чека.
5. `PATCH /api/cases/{id}/transactions/{tx_id}` — пояснить («перевод от мамы» → `category: personal`).
6. `POST /api/cases/{id}/submit` — до пункта 5 вернёт 409 со списком недостающего.
7. `GET /api/staff/cases/{id}/report` — сверка, индикаторы, вердикт и черновик запроса.
8. `POST /api/staff/cases/{id}/decision` или `.../request-docs`.
9. Повторить с `dropper_*` и `block_reason: transit` — вердикт `high_risk`.

## Что внутри

```
app/
├── main.py                 сборка FastAPI-приложения
├── core/                   настройки (config.py) и общие утилиты (validators.py — ИНН)
├── db/                     всё про БД
│   ├── session.py          engine, сессия, Base, init_db
│   └── repository.py       запросы: кейс, очередь, журнал событий
├── models/                 описания данных
│   ├── enums.py            статусы, основания, категории — общие для БД и API
│   ├── orm.py              таблицы SQLAlchemy
│   ├── lknpd.py            формат API «Мой налог»: что он принимает и отдаёт
│   └── schemas.py          схемы запросов и ответов API
├── api/
│   ├── deps.py             зависимости (get_case → 404)
│   └── routes/             client.py, staff.py, analytics.py, bank_core.py (эмуляция банка для демо)
└── services/
    ├── bank/               операции по карте из учётной системы банка (в MVP — эмуляция файлами)
    ├── documents/          приём документов от клиента: разбор чеков и сохранение файлов
    ├── review/             сверка: matching, risk, checklist, report
    ├── analytics/          метрики пилота и финмодель
    └── npd.py              статус НПД в ФНС
```

| Модуль | Что делает |
|---|---|
| `services/bank/` | Операции по карте клиента из банка: при создании кейса и по кнопке сотрудника. Пояснения клиента при повторной загрузке сохраняются |
| `services/documents/parsers.py` | CSV/XLSX выписки с разными названиями колонок, чеки JSON (ответ `GET /api/v1/incomes` «Мой налог», одна или несколько страниц) / CSV / XLSX, автокатегории операций. Неполная выгрузка (`hasMore`, пропуск страницы) не принимается |
| `services/documents/upload.py` | Приём документа от клиента: разбор чеков, сохранение на диск, замена прошлой выгрузки чеков |
| `services/review/matching.py` | Поступления ↔ чеки: 1:1, несколько платежей под один чек, один платёж под несколько чеков; окно — до 9 числа следующего месяца (422-ФЗ) |
| `services/demo.py` | Три демо-кейса для экрана сотрудника (`POST /api/demo/seed`) |
| `static/staff.html` | Экран сотрудника: очередь, вердикт, индикаторы, пары «платёж ↔ чек», решение (`/staff`) |
| `services/review/checklist.py` | Обязательные документы по основанию запроса, период выписки ≥ 90 дней, пояснение к каждому поступлению без чека |
| `services/review/risk.py` | Покрытие чеками, лимит 2,4 млн, транзит за 24 ч, наличные, уплата НПД (4% / 6% по `incomeType`), число плательщиков, ночные операции, аннулированные чеки с разбивкой «ошибочно» / «возврат», чужой ИНН в чеках, поздние чеки по `requestTime`, **доля поступлений, которые клиент сам отнёс к личным** (так нельзя спрятать доход без чеков) |
| `services/review/report.py` | Сводка для сотрудника и черновик точечного запроса |
| `services/npd.py` | Проверка статуса НПД через statusnpd.nalog.ru (`NPD_CHECK_ENABLED=true`) |
| `services/analytics/` | Метрики пилота (часы до решения, число кругов запросов) и финмодель с тремя сценариями — те же допущения и формулы, что в `финмодель.xlsx` (проверяется тестом) |

ИИ здесь сознательно не используется: сверка сумм и дат надёжнее и объяснимее на правилах.
Решение всегда принимает сотрудник, система показывает факты и пороги.

## Ограничения MVP

- Нет авторизации: клиентские и staff-ручки открыты.
- Учётная система банка эмулируется файлами `samples/bank_core/<ИНН>.csv`. В рабочей версии — запрос к АБС ВТБ.
- Чеки клиент загружает сам. В рабочей версии каждый чек стоит сверить с ФНС по его номеру.
- Допущения финмодели (`app/services/analytics/finmodel.py`) совпадают с таблицей; при изменении меняйте оба места.
- Клиенту в чек-листе показывается только число операций, которые осталось пояснить, — значения индикаторов риска остаются у сотрудника (115-ФЗ).
- SQLite и `create_all` вместо миграций: при изменении таблиц демо-база пересоздаётся, данные теряются.
- API «Мой налог» неофициальный, поля сверены с открытым клиентом [shoman4eg/moy-nalog](https://github.com/shoman4eg/moy-nalog).
